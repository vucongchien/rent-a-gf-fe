## 1. Tổng Quan Giải Pháp

Xây dựng khu vực `(admin)` cho ứng dụng Next.js App Router phục vụ vận hành nội bộ. Vai trò Admin duy nhất, toàn quyền. UI tiếng Việt, ưu tiên desktop ≥ 1024px, dùng design tokens pastel hiện có.

**Phạm vi giới hạn ở FE + BFF** — mọi business logic do BE microservices xử lý. FE render dữ liệu BE trả về và gọi đúng endpoint khi Admin thao tác. BFF dùng Next route handlers (`app/api/admin/.../route.ts`) đóng vai proxy + adapt response shape khi cần.

**Sau khi rà API draft:** chỉ giữ các page/feature có endpoint BE tương ứng. Các trang thuộc P1/P2 không có API → DROP khỏi scope MVP, chờ BE bổ sung mới đưa vào plan sau.

## 3. Layout & Navigation

- **`app/(admin)/layout.tsx`** — sidebar trái cố định + topbar (user menu, logout) + content area.
- **Sidebar** chỉ có 2 nhóm: *Người dùng* (Companions) và *Vận hành* (Disputes). Client detail truy cập qua deep link (vd từ dispute → reporter).
- **Auth guard**: middleware gọi `GET /api/auth/me` (BFF wrap, theo `api-contract.md` §3). Role `admin` → cho qua; khác → redirect `/login?reason=forbidden`. Cover BR-001.
- **Global nav reset**: layout admin KHÔNG render global nav của Client/Companion.
- **Loading / error boundaries**: dùng `loading.tsx` + `error.tsx` của App Router ở mỗi segment.

## 4. Service Layer / BFF Strategy

FE component → service module (`xxxService.method()`) → BFF route handler (`app/api/admin/.../route.ts`) → BE microservice (`/api/v1/...`). BFF chịu trách nhiệm forward Bearer token, normalize error shape (gRPC-Gateway → `{ error: { code, message, field? } }` theo `api-contract.md` §2).

**Service modules cần tạo** (`my-app/src/services/admin/`):

| Module | Trách nhiệm | BE endpoints |
|---|---|---|
| `adminAuthService` | Verify session (admin role), logout | `GET /api/auth/me`, `POST /api/auth/logout` |
| `adminUpgradeRequestService` | List pending requests, approve, reject | `GET /admin/upgrade-requests`, `PUT /admin/upgrade-requests/{id}/approve|reject` |
| `adminAccountService` | Lấy chi tiết account, lock/unlock | `GET /admin/accounts/{id}`, `PUT /admin/accounts/{id}/lock|unlock` |
| `adminDisputeService` | List, detail, resolve dispute | `GET /disputes`, `GET /disputes/{id}`, `POST /disputes/{id}/resolve` |

> Mỗi service expose async methods. Endpoint BE đã chốt — chỉ cần BFF wrap.

## 6. State / Data Fetching

**TanStack Query v5** cho mọi data fetching client-side.

**Quy ước:**
- Query keys: `['admin', 'upgrade-requests', { page }]`, `['admin', 'account', id]`, `['admin', 'disputes', { status, page }]`.
- Mutation thành công → `queryClient.invalidateQueries(['admin', 'upgrade-requests'])` hoặc key tương ứng.
- Mọi mutation kèm toast (success / error).
- Polling: KHÔNG cần vì đã DROP dashboard. Nếu sau này cần realtime cho disputes, dùng SSE `/api/sse/user` event `BOOKING_DISPUTED` (theo `api-contract.md` §9).

## 7. Audit Log / Reason Capture (FE side)

FE **không tự ghi** audit log — BE chịu trách nhiệm. FE đảm bảo UX theo BR-003 / BR-005 / BR-013:

- Mọi action write/destructive (approve upgrade, reject upgrade, lock, unlock, resolve dispute) PHẢI đi qua `ConfirmDialog`.
- Action yêu cầu lý do PHẢI dùng `AuditConfirmModal` với validation `reason.length > 0` trước khi enable nút xác nhận:
  - Reject upgrade (`PUT /admin/upgrade-requests/{id}/reject` body `{ reason }`)
  - Lock account (`PUT /admin/accounts/{id}/lock` body `{ reason }`)
  - Resolve dispute (`POST /disputes/{disputeId}/resolve` body `{ resolution, notes }`)
- Sau khi API success → toast "Đã ghi nhận hành động". 409 conflict (đã xử lý bởi admin khác) → hiển thị message từ BE + refresh state.

## 10. Test Architecture (Gọn)

- **Unit (Vitest)** — service module với BFF mocked qua MSW, helper validate `reason.length > 0`. Target ≥ 80% lines cho helpers + services.
- **Component (React Testing Library)** — `DataTable` (empty / loading / error / pagination), `AuditConfirmModal` (disable submit khi reason rỗng), `StatusBadge` render đủ enum.
- **E2E (Playwright)** — chỉ golden path:
  1. Login admin → /admin/companions → list có dữ liệu.
  2. Mở upgrade request → Approve → toast success.
  3. Reject upgrade request với reason → toast success.
  4. Lock account với reason → status đổi sang `LOCKED`.
  5. Mở dispute → Resolve `REFUND_CLIENT` với notes → status đổi `RESOLVED`.
- **No** load / contract / performance test ở giai đoạn này.

## 12. Risks & Open Items

- **R1 — Scope cắt sâu:** Chỉ còn 4 trang IN SCOPE. Stakeholder cần xác nhận MVP admin chấp nhận giới hạn này (không có dashboard, bookings, scenarios, kyc, settings...).
- ~~**R2 — Không có "split" cho dispute resolution**~~ — **CLOSED 2026-06-22**: PO chốt bỏ option chia đôi.
- **R3 — Không có admin booking management:** disputes ra quyết định `REFUND_CLIENT` / `PAYOUT_COMPANION` đã đủ xử lý dòng tiền dispute. Cancel booking thường (ngoài dispute) không có entry point cho admin — chờ BE.

- **R5 — Re-evaluate khi BE mở rộng:** mỗi khi BE bổ sung endpoint mới (bookings list, scenarios admin, kyc...) → mở Wave 2/3 tương ứng.
